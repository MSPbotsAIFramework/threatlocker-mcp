## Requirement understanding

One line: Manage application allowlisting, ringfencing policies, and audit activity via ThreatLocker.

The ticket is the one-line connector-catalogue blurb for ThreatLocker (also shown verbatim at
https://conduit.wyre.ai/plugins/threatlocker, which is a reference link, not an additional
requirement — fetched and confirmed it repeats the same sentence with no extra detail). It names
three capability areas rather than a specific bug or a named tool. Read against the existing
`threatlocker-mcp` connector (`references/mcp-track.md` 2.1, "no specific new requirement, but the
tool table doesn't cover everything the description says"): audit activity is already covered by
three read tools; application allowlisting and ringfencing policies are described as things an
agent should be able to **manage**, and the current connector is read-only end to end. The gap
between "manage" and "read-only" is the actual, concrete ask this ticket resolves to.

## Product design

### Goals / Non-goals

Goals:
- Let an agent act on a ThreatLocker approval request (approve, reject, ignore), not just read it —
  this is what "manage application allowlisting" adds over the existing read tools.
- Let an agent read a specific ringfencing policy, check whether an organization/its computers are
  eligible for Ringfencing, and opt the organization into Ringfencing — the "manage ringfencing
  policies" capability that the public Portal API actually exposes.

Non-goals (explicit, so scope doesn't silently expand during development):
- Creating, editing or deleting the rule content of a ringfencing policy (which processes/network/
  storage calls a fenced app may make). Not possible with the public Portal API today — see Current
  state. If ThreatLocker later documents a write endpoint for this, it is a new ticket.
- "Take ownership" / escalate / assign a reviewer to an approval request
  (`ApprovalRequestUpdateForTakeOwnership`). The ticket asks for allowlisting management, which
  reads as "decide the request" (approve/reject/ignore), not triage/ownership workflow. Listed here
  so a reviewer can see it was considered and intentionally left out, not missed.
- Legacy ringfencing migration tooling (`HasLegacyPolicy`, `ConvertLegacyRingfencePolicy`,
  `GetRingfenceAgentVersion`). Niche, not implied by the ticket text, would roughly double the
  surface added for a capability nobody asked for (YAGNI).
- Creating new approval requests, new computer-group assignments, or application definitions — the
  ticket's three capability areas don't ask for any of this.
- Any change to the per-role tool allowlist/gateway behaviour. That lives outside this repo
  (Current state).

### Acceptance criteria AC1..AC10

- AC1: Given a pending ThreatLocker approval request id, when the agent calls the approve tool with
  that id (and an optional message), then ThreatLocker records the request as authorized for permit
  and the tool returns a result that names the approval request id and the action taken.
- AC2: Given a pending approval request id and a reason, when the agent calls the reject tool, then
  ThreatLocker records the request as rejected/denied and the tool result reflects that outcome.
- AC3: Given a pending approval request id and a reason, when the agent calls the ignore tool, then
  ThreatLocker records the request as ignored and the tool result reflects that outcome.
- AC4: Given an approval request id that does not exist, is already resolved, or is not a GUID, when
  any of the three allowlisting-management tools (approve/reject/ignore) is called with it, then the
  tool returns the existing structured error envelope (`{"error": {"code": ..., "message": ...,
  "retryable": ...}}`) instead of raising, and ThreatLocker's state is unchanged.
- AC5: Given a ringfencing policy id, when the agent calls the ringfencing-policy read tool, then it
  returns that policy's current data, or a `not_found` error envelope if the id doesn't exist.
- AC6: Given valid credentials, when the agent calls the ringfencing-eligibility tool, then it
  returns whether the organization (and its computers) can be enrolled in Ringfencing.
- AC7: Given an organization not yet enrolled in Ringfencing, when the agent calls the ringfencing
  opt-in tool, then ThreatLocker enrolls the organization and the tool returns a success result.
- AC8: Given a call to any of the 6 new tools without the required ThreatLocker headers
  (`X-Threatlocker-Api-Key` / `X-Threatlocker-Organization-Id`), then the tool returns the same
  `not_configured` error the existing read tools already return — no new, inconsistent error shape.
- AC9 (multi-tenant): Given two calls that carry two different `X-Threatlocker-Organization-Id`
  values, when either calls approve/reject/ignore/opt-in, then the action is scoped only to the
  organization id sent on that specific call's headers — never the other tenant's, and never a
  cached one from an earlier call.
- AC10 (no silent no-op): Given any of the 6 new tools succeeds, when its result is returned, then
  the result names what was done (tool name context + the id acted on) so the calling agent/user has
  something to log or show, consistent with every existing tool already returning a JSON string that
  identifies what it read.

### Open questions

- [non-blocking] ThreatLocker's public swagger doesn't publish a response-body schema for
  `ApprovalRequestAuthorizeForPermitById` / `UpdateForReject` / `UpdateForIgnore` / `RingfencePolicy/OptIn`
  (just `200 OK`, no schema) — Tech design §5 covers how the tool shapes a result defensively
  regardless of what the upstream body turns out to contain. Confirming the exact body is dev-leg
  work against a live call, not a design blocker: the request side (path + body fields) is fully
  specified from the swagger, which is what determines the tool's input contract.
- [assumed] "Manage ... allowlisting" is read as decide-the-request (approve/reject/ignore), not
  triage/ownership (see Non-goals). If product actually wants the ownership/escalation workflow
  too, that is additive — a second small change, not a rework of this one.

## Tech design

### Conclusion

Extend the existing `threatlocker-mcp` connector (no new repo, no new service) with 6 new tools in
the same FastMCP server: 3 mutating approval-request actions (approve/reject/ignore) and 3
ringfencing tools (get, eligibility, opt-in). Same client, same per-request credential model, same
error envelope, same pagination/arg helpers already in `_common.py` — this is additive surface on a
pattern that's already proven in this repo, not a new mechanism.

### Data & API contract

All 6 new tools call `https://portalapi.{instance}.threatlocker.com/portalapi/...` exactly like the
existing 17 (same `Authorization: <raw key>` + `ManagedOrganizationId` headers, same instance
detection). Request/response shapes below are read from the vendor's public spec
(`.../swagger/public/swagger.json`, `openapi 3.0.4`, read 2026-10-30); **the 200 response has no
documented body schema for any of the 4 mutating endpoints below** (swagger says `200: OK` with no
content schema) — each tool treats a successful call as `{"approvalRequestId"/"ringfencePolicyId":
<input>, "action": "<approve|reject|ignore|opt_in>", "result": <raw upstream body, possibly empty>}`
so the output is self-describing even if ThreatLocker returns little or nothing. Error path is
unchanged: non-2xx → `ThreatLockerClient` raises `ThreatLockerError` → `to_envelope()` → the same
`{"error": {"code", "message", "retryable"}}` shape every existing tool already returns
(`api_client.py:117-126`, `_STATUS_TO_CODE` table).

**`threatlocker_approvals_approve(approvalRequestId, message?)`**
→ `POST ApprovalRequest/ApprovalRequestAuthorizeForPermitById`
```json
{"approvalRequestId": "<guid>", "message": "<message or \"\">"}
```

**`threatlocker_approvals_reject(approvalRequestId, reason)`** /
**`threatlocker_approvals_ignore(approvalRequestId, reason)`**
→ `POST ApprovalRequest/ApprovalRequestUpdateForReject` / `.../ApprovalRequestUpdateForIgnore`.
Both endpoints take the same body shape (an array of the full `ApprovalRequestDto`, 64 fields, plus
reason/notification fields) — there is no lighter-weight "reject/ignore by id" endpoint in the
public spec. The tool fetches the DTO first (reuses the same call `threatlocker_approvals_get`
already makes, `ApprovalRequest/ApprovalRequestGetById`), then posts it back:
```json
{
  "approvalRequestDtos": [ /* the fetched ApprovalRequestDto, unmodified */ ],
  "responseReason": "<reason>",
  "notifyOnResponse": false
}
```
(`ignoreReason`/`notifyOnIgnore` instead of `responseReason`/`notifyOnResponse` for the ignore call —
same two-field pattern, different key names per the spec.) If
`ApprovalRequestGetById` 404s first (id doesn't exist), the tool returns that `not_found` envelope
without calling reject/ignore at all — AC4's "no partial state change".

**`threatlocker_ringfence_get(ringfencePolicyId)`** → `GET RingfencePolicy/{ringfencePolicyId}`, no
body, returns the policy as-is (schema not published; passed through like every existing `.get`
read tool already does for untyped upstream payloads, e.g. `threatlocker_computers_get`).

**`threatlocker_ringfence_eligibility()`** → `POST RingfencePolicy/Eligibility`, empty body (per
spec, this endpoint takes only the standard org headers, no request fields).

**`threatlocker_ringfence_opt_in()`** → `POST RingfencePolicy/OptIn`, empty body (same: org headers
only, no request fields per spec).

No DB changes (this repo has no database). No event/message changes. Backward compatibility: purely
additive — none of the 17 existing tool names, parameters or behaviours change.

### Key flow / sequence

Reject (the most involved of the 6; approve/ignore/opt-in are single-call):

1. Agent calls `threatlocker_approvals_reject(approvalRequestId, reason)`.
2. Tool calls `GET ApprovalRequest/ApprovalRequestGetById?approvalRequestId=...` (same call
   `threatlocker_approvals_get` makes).
3. If that 404s / errors → return the envelope immediately, no further calls (AC4).
4. Otherwise, build `{"approvalRequestDtos": [<fetched dto>], "responseReason": reason,
   "notifyOnResponse": false}` and `POST ApprovalRequest/ApprovalRequestUpdateForReject`.
5. Wrap the result as `{"approvalRequestId": ..., "action": "reject", "result": <upstream body>}`
   and return it as the tool's JSON string, same as every existing tool's return convention.

### Non-functional

- **Idempotency & concurrency**: none of the 4 mutating tools are idempotent at the application
  layer — calling approve twice on an already-approved request is expected to come back as an
  upstream error (surfaced via the existing envelope, not a new error shape). No local state is
  kept, so there is nothing for two concurrent calls to corrupt in this process; ThreatLocker itself
  is the single source of truth and arbitrates conflicting actions. `ToolAnnotations` is set to
  `idempotentHint=False, destructiveHint=True` for the 4 mutating tools so MCP clients that respect
  annotations don't auto-retry or auto-approve them silently.
- **Performance**: one HTTP round trip per tool call (two for reject/ignore: get-then-post), reusing
  the shared `httpx.AsyncClient` connection pool and the existing `_CALL_BUDGET_SECONDS = 100`
  retry/backoff budget (`api_client.py:34-36`). No new performance profile beyond what the existing
  paginated list/search tools already exercise.
- **Security**: these are the first mutating, security-relevant actions this connector exposes
  (approving software to run, or enrolling an org in a security control). The MCP server adds no
  authorization of its own beyond the caller's ThreatLocker API key — same model as every existing
  tool (`README.md:95-98` "Authentication headers"); the key must itself carry ThreatLocker-side
  write/approval permission (README change above). Per-tool allow/deny-by-default gating is the
  gateway's job, not this repo's (Current state) — an org admin must explicitly allow the 6 new
  tools for a role before an agent can call them, same as any other tool becoming available here.
  No interactive confirmation inside the server: this repo's own precedent
  (`README.md:208-209`, "No interactive prompts... a stateless gateway cannot relay") rules out a
  mid-call confirmation step, so the one safety lever available to this repo is requiring an explicit
  `approvalRequestId`/`ringfencePolicyId` per call — no "approve all pending" tool is added (kept out
  deliberately, not an oversight).
- **Multi-tenant isolation**: every new tool goes through the same per-request
  `ThreatLockerClient(credentials)` construction as the 17 existing tools — credentials (including
  `organization_id`) come from that single request's headers only, never cached or reused across
  calls (`api_client.py:142-150` is the only cache, keyed by a hash of the API key for *instance*
  detection, not organization id, and holds no org-scoped data). AC9's test makes this explicit for
  the new write paths.
- **Observability**: log `tool name + organization id` (never the API key — `ThreatLockerCredentials.__repr__`
  already redacts it, `api_client.py:134-139`) on every mutating call at INFO level, matching the
  existing `logger.info("threatlocker_api detected instance=%s", ...)` pattern (`api_client.py:177`).
  No request/response bodies are logged (none are today either).

### Rollout & rollback

No feature flag, no DB migration, no staged rollout mechanism in this repo — releases are
"merge to `main` → publish to INT" (handled by the review leg per `mcp-track.md` §3/§4). Because the
change is purely additive (6 new tool names, 0 changes to the 17 existing ones), rollback is a
straight revert of the merge commit and re-publish; no existing caller is affected either way.

### Effort & breakdown

Rough order of magnitude: 1–2 dev-days. Natural single-PR scope (one repo, additive, no migration);
no sub-task split needed — splitting "approvals write" from "ringfencing" would just mean two PRs
touching `navigation.py`/`server.py`/`README.md` each, more merge friction for less parallelism.

### Risks & dependencies

- **Risk**: ThreatLocker's actual response body for the 4 mutating endpoints may differ from the
  defensive wrapper assumed here once tested live. Mitigation: the wrapper always includes the
  caller's own input (id + action), so the tool is useful even if the upstream body is empty;
  adjusting what else gets included is a small, local change in the dev leg, not a redesign.
- **Risk**: a ThreatLocker API key without write/approval permission will make the 4 mutating tools
  fail with `unauthorized` for every call even though the connector itself is healthy. Mitigation:
  README documents the permission requirement (Change list); the error envelope already
  distinguishes `unauthorized` from other failures, so this is diagnosable from the tool's own
  output.
- **Dependency**: none on another ticket or unmerged change. Depends only on the public ThreatLocker
  Portal API already in production use by this repo's existing 17 tools.
- Not a risk, a stated boundary: ringfencing rule-content management is not possible with the
  current public API (Current state, Non-goals) — this is a vendor API limitation, not something
  this design can work around.
